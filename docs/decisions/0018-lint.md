# 0018. The linter: rules over the semantic model, a control-flow graph, and quiet when unsure

- **Status:** Accepted
- **Date:** 2026-10-26

## Context

The linter's job is the bugs clang accepts: ABI violations, broken address materialization, stack imbalance, unreachable code. They need more than syntax: which instruction writes which register, where functions start and end, and what happens to sp on every path. A rule that fires on correct code teaches people to ignore the linter.

## Decision

- **Rules work from `arm_sema::Analysis`**: its items (labels, instructions with clang-model operands, sections, data, macro calls), symbols, and references. A rule has an ID (`group/name`), a default level, a one-line summary, and an explanation; `docs/lint.md` is generated from them and a test keeps it in sync.
- **The first rules:** `abi/x18-reserved`, `abi/stack-alignment`, `abi/frame-pointer`, `abi/link-register`, `abi/callee-saved`, `addr/adrp-pageoff`, `addr/variant-mismatch`, `flow/unreachable`, `flow/fallthrough`, `flow/unbalanced-stack` (warnings), and `style/unused-label` (a hint).
- **Functions** start at labels that are exported or called with `bl`. A function's body is what's reachable from its entry through a file-wide control-flow graph, not the lines up to the next label: hand-written code often lays one function's blocks after another's `ret`. A branch to another function's label leaves the function, like a tail call.
- **Stack balance** is dataflow over that graph: sp's offset from entry along every path, checked at each `ret` and tail call. A path where sp is set in a way we don't follow (`mov sp, x29`), or two paths that disagree, makes the offset unknown, and unknown is never reported.
- **Quiet when unsure:** function rules skip functions that reach a macro call or operands we couldn't read. The link-register and frame-pointer rules skip functions that never return, like an entry point ending in the exit syscall, and a final `svc` counts as an ending. Labels starting with `L` or `l` are assembler temporaries and are never "unused".
- **Configuration:** `armtool.toml`, the nearest one above each file, sets levels per rule (`error`, `warning`, `info`, `hint`, `off`). Unknown rules and levels are errors with a suggestion. `; armtool: allow(rule)` on a line, or the line above, silences it there.
- **Where it runs:** `armls` publishes lint findings with the other diagnostics, with the rule ID as the code; a broken config shows as a diagnostic, not silence. `armtool lint` prints `path:line:col: severity[rule]: message` or `--json`, and exits 1 on errors or warnings (hints and info don't fail CI), 2 on usage or config problems.

## Consequences

- On the corpus, compiler output from clang (O0 and O2) has no findings. On HelloSilicon's hand-written code, the one warning left is a real one: a function that saves x30 and calls another but never sets x29.
- Register writes come from a short list of instructions whose first operand is read, not written, plus pair loads and writeback. A new instruction with an unusual operand order can be misread; such a rule errs toward silence where it can.
- Deeper dataflow (register liveness, reads of undefined registers) can reuse the graph.

## Alternatives considered

- **Functions as the lines between labels.** Simple, and wrong on real hand-written code, where it blamed one function for another's calls.
- **Report when unsure.** More findings, and some false: the wrong tradeoff for a linter people should trust.
- **A separate config format or comment syntax per tool.** One file and one comment form for both armls and armtool.
